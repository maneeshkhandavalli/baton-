# Demo plan (Phase A): interactive CodeCell sandbox

Agent `demo`, 2026-11-15. Read with `audit.md` (what exists) and `scenario.md` (the story). The reuse contract with
`handover` is **agreed** (their reply on 2026-11-15; recorded in `collab/handover/plan.md`, "Demo seams"). This plan
chooses no colours, fonts or components; visual decisions belong to `brand`'s design system.

## 1. Principles

1. **Real screens, demo data.** Steps 3–6 render `handover`'s real views (review workspace, publish dialog, published
   handover, gaps manager, Gap Interview), and step 1 uses the real wizard step components, all fed from a client-side
   store. No look-alikes.
2. **Nothing leaves the browser.** No server actions, no Supabase, no AI, no email, no working links, no shared server
   memory. This is enforced by a static import-graph test and a runtime network check (§4), not by convention.
3. **Honest about what is simulated.** Anything the demo fakes (the AI draft, the processing run, re-checks after the
   visitor's own edits, notifications) carries a visible label (§5).
4. **One consistent story.** All data comes from `lib/demo/scenario` (tested against the real parser and masker). The demo
   runs on a fixed scenario clock.
5. **Free to explore, easy to follow.** Visitors can take any review action in any order. A suggested path (the canonical
   actions) guides them, and "jump to step N" plus Reset always recover a coherent state.

## 2. Architecture

```
app/(marketing)/demo/page.tsx        server: metadata + static shell, renders <DemoSandbox/> (no data fetching,
                                     no lib/mocks queries, no connection(): can be prerendered)
components/demo/demo-sandbox.tsx     "use client": owns the demo store (useReducer), persona, current step
components/demo/steps/*              one component per step; each composes handover's VIEWS with demo adapters
components/demo/chrome/*             step navigation, persona bar, annotations (data-tour anchored), reset, labels
lib/demo/scenario/*                  DONE: cast, sources, points, gap questions, timeline, canonical actions
lib/demo/engine/store.ts             buildDemoStore(): a MockStore holding ONLY the demo handover, built from the
                                     scenario with lib/mocks/fixtures/builders (buildPoint) and lib/mocks/types
lib/demo/engine/actions.ts           pure reducers (store, actor, clock, input) → { store, result: Result<T> } with the
                                     SAME input/output types as the real server actions (ported subset of
                                     lib/mocks/actions.ts: reviewPoint, createGapQuestion, publishHandover,
                                     startRevision, createGapInterviewLink, submitGapAnswers, reviewGapAnswer,
                                     acknowledgePublication)
lib/demo/engine/selectors.ts         DTOs per persona: HandoverSummary, PointDetail[], ReadinessReport,
                                     GapQuestionSummary[], SourceSummary[], PublishedHandover, GapInterview,
                                     ProcessingStatus. Uses lib/mocks/derive.ts (canonical status/readiness/snapshot).
lib/demo/engine/script.ts            replay(canonical actions up to step N) → that step's starting store
lib/demo/engine/clock.ts             step clock: DEMO_STEP_CLOCK[step] + 1 minute per action (never Date.now())
lib/demo/engine/adapters.ts          makeDemoActions(dispatch) → ReviewActions, GapsActions, GapInterviewActions,
                                     PublishedActions (objects with the real signatures; resolve after ~250 ms so
                                     pending states show; no network)
lib/demo/scenario/generated/*.ts     masked transcripts of the three sources for step 1, generated by a script with
                                     the real parser; a test fails if they drift from sources.ts
```

**Where state lives.** All of it is in `DemoSandbox`'s reducer state: one `MockStore` value (only the CodeCell demo
rows), the persona (`priya | neha | ananya`), the step, and the annotation progress. Reducers copy the store
(`structuredClone`) and mutate the copy, so the ported mock logic stays almost verbatim. Optional per-tab persistence:
the state is serialised to `sessionStorage` (key `baton:demo:v1`, wrapped in try/catch), so a reload keeps progress. If
storage is missing, the demo simply starts at step 1.

**Reset.** "Start over" restores `buildDemoStore()`, step 1 and persona Priya. It clears `baton:demo:*`, the demo's
first-week ticks (`storageNamespace="baton:demo:first-week"`, agreed with `handover`), and turns off Gap Interview draft
persistence (`draftStorageKey={null}`, agreed). "Jump to step N" = `replay(N)`. The step navigation warns when a jump
would discard the visitor's own changes.

**Why not the existing server-side mock.** `lib/mocks/store.ts` is one process-wide `globalThis` store shared by every
visitor, and `lib/mocks/actions.ts` is `"use server"`. Using either would mean visitors writing into shared server memory.
`lib/mocks/queries.ts` imports `next/server` (`connection`), so client code cannot use it. The demo reuses only the pure
modules (`derive.ts`, `builders.ts`, `ids.ts`, `exclusions.ts`, `types.ts`) and changes nothing in `lib/mocks`.
Alternative, if `handover` and `main` prefer less duplication: extract the action logic in `lib/mocks/actions.ts` into
pure `lib/mocks/engine/*.ts` functions shared by both. That changes `lib/mocks`, so it needs their agreement. I am not
asking for it now. A parity test (§6) keeps my port honest instead.

**Re-verification.** The real product re-checks quotes with AI after an edit; the demo cannot. For the canonical edits the
result is scripted (`ScriptedReverify` in `journey.ts`) and appears after a short "re-checking…" state, like the real one.
For any other edit a visitor makes, the engine keeps the previous verdicts, marks the point "Not re-checked in the demo"
and explains why. Approving such a point is still allowed, as it is in the product.

**Personas and permissions.** Selectors compute each view at the persona's clearance: Priya is the creator at
reviewer_only; Neha is incoming at everyone, so leads-only points disappear and the demo says so; Ananya sees only the Gap
Interview questions in her link's scope. Reducers apply the same permission and lifecycle checks as the mock actions. For
example, Neha cannot approve and publishing needs readiness, so visitors meet the product's real rules.

**Routing (to verify against `node_modules/next/dist/docs` before Phase B code).** A single route `/demo`. The step is
in the URL as `?step=sources|draft|review|decisions|publish|receive` (read on the client inside `Suspense` and updated with
`router.replace`, no server round trip). A deep link opens that step's replayed state. The current `/demo` content
(read-only tabs) stays until the new sandbox replaces it in one change.

Global controls: step navigation (6 steps, done/current/next, keyboard reachable), persona indicator, "Start over",
"What's simulated here?" (a short list), and per-step annotations that can be dismissed or brought back. On mobile the
step navigation becomes a compact "Step 3 of 6" bar with previous/next, and annotations become inline notes above the
content, never floating popovers that cover the screen. The review workspace keeps its own mobile layout (readiness in
`<details>`, detail sheet).

Accessibility: a step change moves focus to the step heading and announces "Step N of 6: …" in a polite live region;
annotations are plain text in the reading order (not tooltips only); timers respect `prefers-reduced-motion`; every
"do it for me" action is an ordinary button.

## 4. Guarantees: no writes, no AI, no external calls

1. **Static import graph (test).** `lib/demo/__tests__/isolation.test.ts` resolves every import reachable from
   `app/(marketing)/demo/**`, `components/demo/**` and `lib/demo/**` with the TypeScript resolver, and fails if it reaches
   `lib/actions`, `lib/db`, `lib/supabase`, `lib/ai`, `lib/pipeline`, `lib/data`, `lib/mocks/{actions,store,queries}`,
   `@supabase/*`, `@google/genai`, `next/cache` or `server-only`. This becomes possible because `handover` is splitting the
   views from the action-bound wrappers (agreed).
2. **No network primitives (test).** The same test forbids `fetch(`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`,
   `EventSource` and `"use server"` in demo-owned files.
3. **Runtime check (CDP script).** A headless walk through the whole canonical path records every request and fails on
   any POST (server actions are POSTs with a `Next-Action` header) or any non-same-origin request after load. Saved under
   `.claude/ui3/shots/demo/`.
4. **No shared server state.** The page does not touch `lib/mocks/store.ts`, so `/demo` no longer depends on server memory.
5. **No real links or messages.** Demo-created Gap Interview links render with `linkMode="demo"`; invites and emails are
   never generated; the only exits are "Start your own handover" (the real sign-in flow) and the site header.
6. **Fixed clock.** Visitor actions carry scenario times, so the demo never stores or shows the visitor's real time.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| My engine drifts from the product's rules (`lib/mocks/actions.ts` and the real actions) | Port the mock logic nearly verbatim; parity test on DTOs; reducer tests copied from the mock's rules |
| `handover`'s split lands late, so the demo can't reuse the views without the action imports | The sandbox engine, scenario, steps 1–2 and the chrome don't depend on it. Steps 3–6 wait for the split rather than adding a temporary fake |
| Visitors make unscripted edits, so re-verification can't be real | Keep verdicts, label "not re-checked in the demo", still allow approval (as the product does) |
| The bundle grows (zod schemas, derive, scenario, transcripts) | All client-side but code-split by step; transcripts are about 6 KB; measure in Phase B |
| `sessionStorage` state from an older demo version breaks the reducer | Versioned key `baton:demo:v1`; discard on mismatch or parse failure |
| Free exploration leaves an unpublishable state | Readiness explains why (the real panel); "do it for me" per correction; jump or reset |
| Persona switches confuse visitors | Persona bar with the name and role, an announcement on switch, step labels naming the persona |
| Two CodeCell stories remain (`lib/mocks` for previews) | Previews are dev-only; the public demo and the samples share one story after the Phase B alignment |
| The demo's Gap Interview and publish could teach wrong product rules | They run the same checks as the real actions (required gaps, readiness, creator-only publish, revision before republish) |
| Add a point (manual points) isn't in the scenario | Hidden in the demo at first (no `createManualPoint`); can be added later with "not re-checked" semantics |
